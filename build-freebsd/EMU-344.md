# EMU-344 — where syscall 344 is served, and why the EINVAL cannot be read

Base: `pr-arm64` = `3c9531647` (the merged `task/readdir-entries`).
No root run. Everything here is either a file in this tree, a symbol in an
overlay binary, or a line of the log `DIR-ENUM.md` already points at.

**Short answer: the handler is `darling-emu`, and that repository is not public.
What this repository carries of it is prototypes and an empty table. So the
`file:line` that returns `EINVAL` cannot be obtained from any public clone, and
I will not write one down. What can be said, and is said below: every hop of
the call that *is* in reach, one prototype header with the handler's exact name
and signature, and one structural difference between the host's directory
records and Darwin's that any re-packer has to know about.**

## 1. The call, hop by hop, with everything that has an address

| hop | where | evidence |
|---|---|---|
| the probe asks for a directory's entries | `tests/src/bundle-principal-class.m` | calls `__getdirentries64` |
| the guest's `readdir` does the same | `libsystem_c.dylib+0x3d5e9` | `callq ___getdirentries64`, disassembled |
| …and drops any record whose inode field is 0 | same function, +0x3d714 | `cmpq $0x0,(%rax)` — the rule `readdir.c:118` compiles to |
| the syscall wrapper | `libsystem_kernel.dylib+0x42dbc` | `movl $0x158,%eax; callq __darling_bsd_syscall` |
| the number | 344 | Darwin `__getdirentries64` (`syscalls.master:344`, listed as such in upstream `src/xtrace/bsd_trace.cpp:291`) |
| mldr's BSD syscall trap | `src/startup/mldr/freebsd_syscall_trap.c` | **does not handle 344** — see §2 |
| the emulation | `darling-emu` | **not public** — see §3 |

The trap is ours and it is a real alternative (§4), but it is not where the
`EINVAL` is born: 344 is not in its dispatch.

## 2. mldr does not handle 344, and that is visible in the file

`freebsd_syscall_trap.c` defines the Darwin syscall numbers it claims
(`MACOS_SYS_*`, lines 154-189) and handles that set locally. `#define
MACOS_SYS___getdirentries64` is not among them, so 344 falls through to the
forwarding path. The only directory code in the whole 3074-line file is the
Linux-ABI re-packer for `LINUX_SYS_getdents64` (around line 2200), which is a
different syscall number on a different ABI and is not what the guest calls.

For the record, the trap does already forward the *Darwin* BSD set straight to
the host with no fd translation — `case MACOS_SYS_read: return
freebsd_raw_syscall(SYS_read, a1, a2, a3, 0, 0, 0);` (line 572),
`MACOS_SYS_open` the same way (line 584). That matters in §4.

## 3. The handler is `darling-emu`, and it is not on GitHub

The layer's own name is in our tree, hundreds of times: the SDK vendors its
headers under
`Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk/usr/include/darling/emulation/`.
Two of them are the ones this wall runs through:

- `xnu_syscall/bsd/impl/dirent/getdirentries.h` — the handler's header:

  ```c
  long sys_getdirentries(int fd, char* buf, unsigned int len, long* basep);
  long sys_getdirentries64(int fd, char* buf, unsigned int len, long* basep);
  ```

  The name and the signature are exact. The body is not in the file.

- `xnu_syscall/bsd/bsd_syscall_table.h` — six lines, and the only one that says
  anything:

  ```c
  extern void* __bsd_syscall_table[600];
  ```

  A declaration of the dispatch table, not the table. The slot for 344 is
  filled from `darling-emu`'s own translation unit.

And the repository is not public. Checked, not assumed:

- `git clone https://github.com/darlinghq/darling-emu.git` → prompts for
  credentials, i.e. not found for an anonymous reader.
- `curl https://api.github.com/orgs/darlinghq/repos` over all pages: **186
  public repositories**, `darling-emu` among none of them. The neighbours are
  all there (`darling-Libsystem`, `darling-Libc`, `darling-dylib`,
  `darling-vchroot`-era pieces, `darling-newlkm`, `darling-stub-gen`), so this
  is not a naming guess.
- `darlinghq/darling` master's `.gitmodules` has no entry for it, and its tree
  has no `src/external/darling` — the layer is fetched outside the repo.
- `darlinghq/darlingserver` was cloned and grepped: it mentions `getdirentries`
  only in `duct-tape/xnu/bsd/kern/syscalls.master`, `duct-tape/xnu/bsd/sys/dirent.h`
  and `vnode_if.h` — headers and the syscall table, no handler.

So the chain ends in a repository that cannot be read from here. That is the
finding, and it is the answer to "назвать файл:строку": there is no such address
in anything public, and the nearest thing is the prototype above.

## 4. Why the selection, and what it cannot be

`DIR-ENUM.md` §2 has the matrix. It refutes path length (`len=26` works,
`len=43` fails beside `len=45`), depth (`/System` fails, `/System/Library`
works), and the framework's name (four frameworks fail under a working parent).
On the host, the staged tree has no symlinks and no odd types anywhere in the
failing chain — every one of those directories is a plain directory.

That leaves the suspicion `DIR-ENUM.md` §4.4 offered — *something about the
specific directory, not about the path* — **standing, and unproven**. I could
not confirm or refute it without the handler, and I am not going to promote a
suspicion to a conclusion because it is the only one left. Two facts do narrow
it:

- `open(path, O_RDONLY|O_DIRECTORY)` succeeds for every directory that the
  listing refuses. So the fd is a real directory fd in the layer's eyes; the
  refusal happens when the records are asked for, not when the fd is made.
- `Info.plist` reads 768 bytes from inside `Wayland.backend/Contents`, the
  directory whose listing returns `EINVAL`. Reading and listing disagree about
  the same directory.

A handler that answers `EINVAL` — rather than `ENOENT` or `EIO` — is answering a
*validation*, so the first thing to read in `sys_getdirentries64` is whatever
validates. On the evidence above it validates something about the directory,
not about the path length and not about the fd.

## 5. A second, separate defect in the same call

Worth separating from the `EINVAL`, because it is measurable and it is not the
same bug. The successful calls return far less than the directory contains:

| guest path | entries on the host | bytes the syscall returned |
|---|---|---|
| `/` | 10 | 200 |
| `/System/Library` | 8 | 136 |
| `/System/Library/Frameworks` | 60 | 344 |
| `/usr/lib` | 91 | 392 |
| `/usr/lib/system` | 34 | 364 |

`/usr/lib` has 91 entries and 392 bytes came back — about four bytes per entry,
which is impossible; a Darwin record is 24 bytes of header plus the name. So
even where the call succeeds it returns a small fraction of the directory, and
`readdir` would need several round trips (or gets `EINVAL` on the next one,
which §2 cannot distinguish yet because the log has no second-call trace).

I am reporting this as an arithmetic fact about the log and the host tree, not
as a diagnosed bug: what a correct batch size *should* be depends on how the
layer buffers, and that is in the code I cannot read.

## 6. The two fix sites, evaluated

**(a) In the emulation layer.** Correct in principle — that is where the bug is
— and not available: the repository is not public, so a patch here would be a
patch against a file nobody else can fetch. This becomes an owner question
(where a fixed `darling-emu` lives), not a branch.

**(b) A native 344 handler in `src/startup/mldr`, ours.** Technically small, and
the наряд asked for it to be evaluated by facts. What the facts say:

- *Does mldr own the fd?* Yes. The trap forwards Darwin `read`/`open`/`fstat`
  with the guest's fd passed straight through as `a1` (lines 572, 584, 612).
  There is no fd table to consult, so a 344 handler needs no translation.
- *Can it repack?* Yes, but the layouts are **not** identical, and this is the
  one thing in this document that would silently corrupt a listing if missed.
  Measured on this host (`offsetof`, printed by a throwaway program):

  | field | host FreeBSD ino64 `struct dirent` | Darwin `bsd_dirent64` |
  |---|---|---|
  | `d_fileno`/`d_ino` | 0 | 0 |
  | `d_off`/`d_seekoff` | 8 | 8 |
  | `d_reclen` | 16 | 16 |
  | **`d_type`** | **18** | **20** |
  | **`d_namlen`** | **20** | **18** |
  | `d_name` | 24 | 24 |

  Host `struct dirent` is `{d_fileno, d_off, d_reclen, d_type, d_pad0,
  d_namlen, d_pad1, d_name[256]}` — `sizeof` 280 here. Darwin's is
  `{d_ino, d_seekoff, d_reclen, d_namlen, d_type, d_name[]}` (the struct in
  `conversion/dirent/getdirentries.h`). **`d_type` and `d_namlen` are swapped.**
  A re-packer that memcpy'd the host record would hand the guest a name length
  read from the type byte, and every name after the first would be garbage.
  The two fields have to be moved explicitly.
- *Is that all?* No. The handler would also have to reproduce whatever the
  emulation does with the batch size (§5) and with `basep`, i.e. the parts of
  the contract nobody has read.

**Recommendation: (a), and it is not close.** Not because (b) is impossible —
it is maybe eighty lines — but because (b) would replace one unread
implementation with a second one, in a layer whose current behaviour on failing
directories is exactly the thing nobody can explain yet. Fixing a wall whose
cause is unknown by writing around the wall is how the next person loses a day.
The one-line argument for (b) is that it is the only site in our reach; the
counter is that being the only site in reach is not the same as being right.

If the owner decides (b) anyway, the two things it must do that this document
establishes are: move `d_type`/`d_namlen` explicitly, and answer the §5
truncation rather than inheriting it.

## 7. Not verified

- **No root run**, so the budget from the приёмка was kept. Nothing here needed
  one: every claim is a file, a symbol, an `offsetof`, or a line of an existing
  log.
- **`d_type`/`d_namlen` swapping is a hazard, not an observed fault.** Nothing
  in the logs shows a listing with a wrong type byte; it is what a naive
  re-packer in (b) would do, and the offsets are measured.
- **The selectivity is unexplained.** §4 narrows it to "something about the
  directory" and stops there.
- **§5's truncation is arithmetic, not a diagnosis.** What a correct return size
  is depends on code that is not readable here.
- The `darling-emu` absence was checked against GitHub's public API today; if
  the owner has access to it privately, §4's first step becomes one `grep`.
