# План работ: darling-freebsd

Дата: 2026-08-26. Пересматривать при закрытии каждой ступени.

## North star и измеримая цель — это разные вещи

**North star — Chrome.** Не как задача, а как направление: он заставляет строить
многопроцессность, Mach IPC и графику по-настоящему, и сразу отсекает
упрощения, которые потом пришлось бы выбрасывать.

**Но мерить прогресс по нему нельзя**, и это надо сказать прямо. Chrome сегодня
за пределами состояния всей отрасли, а не только нашего порта: апстримный
Darling с многолетней историей и несравнимо большими силами держит консольные
приложения и **экспериментальную** поддержку Cocoa. Ставить Chrome ближайшей
целью — значит годами не иметь ни одного проверяемого рубежа.

**Измеримая цель — настоящее Cocoa GUI-приложение, выводящее картинку в
wlstream.** Это ровно передний край отрасли, он проверяем, и до него видна
дорога. Chrome добавляет сверху многопроцессность, GPU и sandbox; первые две —
отдельные ступени ниже, а GPU и sandbox обходятся его же флагами
(`--disable-gpu`, `--no-sandbox`) и потому не на критическом пути.

## Где мы сейчас (ступень 0 пройдена)

Динамическая линковка работает, ~41 гостевая dylib на процесс. Работают
настоящие сторонние консольные приложения: неизменённый апстримный `sqlite3`
(`select 21*2;` → `42`) и запись настроек через CFPreferences (`defaults write`
создаёт корректный plist с нужным ключом).

Не работает: `defaults read` (CF возвращает пустой список доменов), создание
процессов, GUI, aarch64.

## Ступени

### 1. Создание процессов

**Почему первая.** Без неё вторая и третья не проверяются даже в принципе, а
Chrome многопроцессный по своей природе (zygote, GPU-процесс, рендереры).
Окупается отдельно: разблокирует `NSTask`, исключённый из сборки Foundation
именно поэтому, и любое приложение, запускающее помощников.

**Состав.** `execve`, `posix_spawn`, корректный `fork` с уведомлением
darlingserver (в протоколе checkin есть флаг `is_fork` — сырой `fork()` его не
шлёт, то есть текущая реализация почти наверняка неверна). Отдельный вопрос —
что происходит с RPC-сокетом при форке.

**Проверка.** python.org-сборка Python: `subprocess`, потоки, файлы. Тяжёлое
реальное приложение без GUI.

**Спецификация.** `docs/SPEC-mldr-process-creation.md`.

### 2. Mach IPC между процессами

**Почему.** У Chrome на Mach-портах построен весь межпроцессный обмен. Мы уже
упираемся в `MACH_SEND_INVALID_DEST` и `KERN_INVALID_NAME` **внутри одного**
процесса, то есть работа начинается ещё до многопроцессности.

**Известный сопутствующий долг.** Механизм прерываний darlingserver у нас не
работает: `InterruptEnter` не объявляется, и протокол ловит устаревшие ответы.
Сюда же — нереентерабельный `Kprintf`, из-за которого штатная отладка libkqueue
непригодна.

**Проверка.** Пара процессов, общающаяся через XPC.

### 3. GUI: `Wayland.backend` для Cocotron

**Это одна из самых дешёвых ступеней относительно эффекта**, и вот почему.

AppKit у Darling — это Cocotron (`src/external/cocotron/AppKit`, 375 файлов).
Он использует плагины-бандлы: абстрактный `NSDisplay` грузит `*.backend` по
приоритету. Единственный существующий — `X11.backend`. Свой бэкенд это подкласс
`NSDisplay` плюс подкласс `CGWindow`, упакованные бандлом. Точка передачи
готового кадра — `CGWindow -flushBuffer`.

**То есть речь не о написании графического стека, а об одном бандле.**

Рисует программный растеризатор Onyx2D в `O2Surface`, владеющий своей памятью;
формат — **BGRA8888 premultiplied, little-endian, плотный stride**. Это байт в
байт `WL_SHM_FORMAT_ARGB8888` на little-endian, то есть конвертация пикселей,
судя по всему, не нужна вовсе.

Обратный канал прост: собрать `NSEvent` и вызвать `postEvent:atStart:`, ничего
X11-специфичного переиспользовать не надо.

**Почему именно Wayland, а не прямая врезка в wlstream.** `wayland-tunnel` —
это Wayland-**сервер**, принимающий клиентов (сейчас `foot`, `chromium`).
AppKit в роли клиента подключается к нему как любой другой, и весь конвейер
`cage → wayland-tunnel → wlstream → зритель`, вместе с вводом, resize и ключами
Zenoh, работает **без единой правки**. Прямая врезка заставила бы заново решать
damage, темп кадров, ввод и resize — то есть переписать уже готовое.

Второй довод приходит со стороны GPU: Vulkan выводит через WSI, и
`VK_KHR_wayland_surface` — стандарт, а «WSI для wlstream» не существует нигде.
Wayland-поверхность объединяет оба пути вывода — программный CoreGraphics и
будущий Metal→Vulkan — вместо того чтобы заставлять выбирать.

**Известные препятствия.** GUI-ветка (`COMPONENT_gui`) в этом порту не
собиралась ни разу. Единственный пример бэкенда, X11, глубоко завязан на Xlib и
выводит даже программно нарисованный буфер через GLX — списать «как есть» не
выйдет.

**Спецификации.** `docs/SPEC-appkit-display-backend.md`,
`docs/SPEC-wlstream-frame-source.md`.

**Проверка.** Примеры из `src/external/cocotron/examples`.

### 4. Metal → Vulkan (позже, в ту же поверхность)

У Darling начат Metal-бэкенд поверх Vulkan — писать Metal с нуля нереально,
заимствование здесь без оговорок.

**Приоритет намеренно низкий:** подавляющее большинство Cocoa-приложений Metal
не используют, обычный AppKit рисует через CoreGraphics программно. Metal нужен
Chrome-классу и играм.

На дев-VM Vulkan сегодня не запустится: установлены только `vulkan-headers`, ни
загрузчика, ни ICD. Реалистичный первый шаг — `vulkan-loader` плюс **lavapipe**
(программный Vulkan): корректность вперёд скорости. Настоящий GPU в QEMU на
FreeBSD — отдельный проект через virtio-gpu venus.

### Не делаем

- **Sandbox и code signing** — Chrome обходится флагами, ничего про
  совместимость они не проверяют.
- **aarch64** — пока не закрыт x86-64.
- **Свой AppKit или форк Cocotron** — обнуляет заимствование у апстрима.
- **Уход на Darwin/XNU вслед за ravynOS.** Для них совместимость была
  продуктом, терять было нечего. У нас FreeBSD несущая: jails и `jailrun`, ZFS,
  kolkhoz, Zenoh-меш, конвейер стриминга. Их вывод верен для их целевой функции
  и не переносится на нашу автоматически.

## Отношения с апстримом

Чем меньше расхождение, тем дешевле забирать их GUI-работу. Большинство наших
правок — специфика FreeBSD и уйдёт наверх только как порт целиком, что является
большой заявкой. Но два исправления самодостаточны и чинят Linux тоже:

1. **`darling-foundation`**: `setPersistentDomain:forName:` использует
   `registerDefaults:`, то есть пишет в энергозависимый `NSRegistrationDomain`,
   который на диск не попадает никогда — `defaults write` не работает и на
   Linux. Рядом `removePersistentDomainForName:` чистит `self` вместо
   названного домена.
2. **`darling-libkqueue`**: в `evfilt_machport_copyout` проверяется только
   `rv < 0`, а `recv()`, вернувший 0, проскакивает как успех, после чего
   неинициализированная структура со стека разбирается как уведомление.

Плюс сообщение (не патч) для `darlingserver`: он молча закладывается на
уникальный адрес у каждого сокета — на Linux это даётся бесплатно через
autobind и нигде не записано.

В описаниях PR честно указывать, что проверено только на FreeBSD.

## Метод

Сегодняшний день дал калибровку, которую стоит удержать. Тринадцать
исправлений, и узкое место было не в написании кода, а в **измерении**: четыре
убедительные гипотезы (`rt_sigreturn`, вложенность `pthread_canceled`, общий
сокет у потоков, `getattrlistbulk`) оказались неверны и были закрыты проверкой,
а не реализацией. Отсюда правила:

- Гипотезу проверять измерением до того, как писать по ней код.
- Заявления субагентов перепроверять по исходникам: сегодня один взял неверную
  структуру, другой построил рекомендацию на неверной посылке, третий нашёл то,
  что было бы пропущено.
- Диагностику, которая себя окупила, оставлять в дереве (`MLDR_LOG_MAPPINGS`,
  `MLDR_TRAP_AT` и прочие) — следующая гипотеза потребует тех же данных.
- Документацию держать в актуальном состоянии: устаревший пункт «dyld не
  сделан» в README уже один раз ввёл в заблуждение исследование.
